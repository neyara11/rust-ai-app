# Локальный и корпоративный режимы

Платформа работает в двух окружениях и с двумя ролями. Окружение выбирается **при
установке**: NSIS-установщик спрашивает «локальный или корпоративный» и записывает
ответ в `%ProgramData%\EcoAIOps\install-mode.json`. Для тихой установки режим
передаётся аргументом `/MODE=`:

```powershell
& ".\ECO AIOps_0.1.0_x64-setup.exe" /S /MODE=corporate
```

Пока этот файл существует, приложение берёт режим из него и **не позволяет менять его
на лету** — команда `--mode` и кнопка «Сменить режим…» возвращают ошибку. Смена режима —
только переустановка (файл удаляется при удалении приложения).

`--mode` остаётся для профилей без установки (разработка, `ECO_PLATFORM_HOME`):

```powershell
eco-platform.exe --mode local user
eco-platform.exe --mode corporate developer
```

Роль (`developer`/`user`) по-прежнему хранится в `config.json` профиля (`environment`,
`role`, `mode_chosen`); для установленной версии `environment` переопределяется
install-mode-файлом.

## Режим разработчика

Окружение фиксируется установкой, но роль переключается без переустановки:

- в UI: Настройки → «Контур доверия» → «Включить режим разработчика» (там же видно
  текущую роль);
- из консоли: `eco-platform.exe --role developer` (обратно — `--role user`).

Роль открывает мастер пакета и авторские вкладки; проверки seal/подписи, trust anchor
и allowlist от неё не зависят и продолжают действовать по выбранному при установке
окружению.

## Матрица

| | Разработчик | Пользователь |
|---|---|---|
| **Локальный** | Ставит любые пакеты (signed/unsigned), мастер пакета, dev-ключи, правка исходников и пересборка. Anchor и allowlist не нужны. | Ставит любые пакеты (signed/unsigned). Установленное приложение менять нельзя. Каталог + чат; мастер пакета скрыт. |
| **Корпоративный** | Авторство под политикой: подпись ключом организации, локальный тест. | Только пакеты, подписанные активным anchor и разрешённые allowlist. Контур задаёт администратор. |

## Что именно проверяется

Три проверки разделены, а не слиты в одну:

1. **Целостность** — `schema_version`, `min_shell_version`, наличие prompt и sha256
   всех файлов из `hashes`. Выполняется всегда.
2. **Неизменность после установки**:
   - корпоративный режим — подпись `manifest.sig` от активного anchor;
   - локальный режим — локальный **seal**: при установке платформа записывает
     sha256 каждого файла пакета в `<home>/seals/<app_id>.json` (без `engine/`,
     `sessions/`, `tmp/`, `attachments/`) и сверяет при каждом запуске. Правка
     промта, скила, скрипта, манифеста или добавление лишнего файла → отказ.
     Исключённые каталоги — состояние платформы: движок, история чатов,
     артефакты и кэш картинок вложений переживают обновление и откат и не
     входят в архив версий.
3. **Авторизация** — allowlist/CRL. Только корпоративный режим.

Локальный seal защищает от случайной или «бытовой» правки. От целенаправленного
локального администратора он не защищает: файл seal принадлежит тому же пользователю
ОС. Для неопределённой группы лиц нужен корпоративный контур с anchor.

Роль `user`/`developer` — это режим интерфейса, а не граница авторизации: она скрывает
мастер пакета, но не отменяет проверку seal/подписи при запуске.

## Пакет с группой скилов

Один пакет может содержать несколько независимых скилов, MCP-подключения и несколько
`bin`-инструментов:

```text
my-app/
├─ manifest.json
├─ prompt/system.md
├─ skills/
│  ├─ main/SKILL.md
│  ├─ helper/SKILL.md
│  └─ helper/scripts/...        # ресурсы скила, покрываются hashes
├─ bin/tool-a.exe
├─ bin/tool-b.exe
└─ manifest.sig
```

- `eco-pack build` рекурсивно хеширует `skills/**` и `bin/**`, поэтому группа скилов
  и их ресурсы попадают в подпись и в seal.
- Если скилов несколько, платформа не склеивает их в промпт: она добавляет индекс и
  инструмент `platform_skill`.
  - `{"action":"list"}` — имена и короткие описания;
  - `{"action":"read","name":"helper"}` — полный `SKILL.md`.
  Модель загружает только нужный скил, зависимости — по мере необходимости.
- Один скил по-прежнему встраивается в промпт целиком (совместимость).
- MCP-серверы объявляются в `connections` (только id и тип `http-mcp`), а порядок
  работы с ними описывается в `AGENTS.md` → `prompt/system.md`. URL и токены в пакет
  не попадают.
- Несколько `bin`-инструментов описываются как несколько элементов `tools[]`;
  у каждого может быть своя JSON-схема аргументов, свой `stream` и свои секреты.

## Подготовка пакета по правилам

1. `AGENTS.md` → `prompt/system.md`; убрать абсолютные пути и команды оболочки,
   заменить их на вызовы инструментов.
2. Скилы положить в `skills/<name>/SKILL.md`; всё, что скил читает, — рядом в его
   каталоге.
3. `.env`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `credentials*` в пакет не
   кладутся. Скрипты читают `os.environ`, имена секретов объявляются в
   `tools[].secrets` и вводятся в платформе (DPAPI). Значения можно задать глобально
   или отдельно для приложения: app-override имеет приоритет, глобальное значение
   используется как fallback.
4. MCP — только id в `connections`; endpoint, токен и TLS-политика задаются в
   настройках платформы. Один id может иметь разные креды в разных приложениях.
   Для private CA/self-signed сертификатов есть отдельный переключатель отключения
   проверки TLS — только для конкретного подключения и с фиксацией в заявке ИБ.
5. `eco-pack validate` → `eco-pack build` → `eco-pack validate`; для локального
   теста — `eco-pack sign` dev-ключом.
6. Абсолютные пути и ссылки на каталог автора в промте/скилах недопустимы: пакет
   должен работать на чужой машине.
