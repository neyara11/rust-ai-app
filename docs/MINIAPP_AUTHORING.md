# Разработка мини-приложения: требования к исходникам

Документ для автора мини-приложения. Проверочный пример —
`examples/file-notes` (навык + работа с файлами). Процесс ролей и подписи —
`docs/APP_LIFECYCLE.md`.

## 1. Что нужно автору

- Windows 10/11.
- Установленная платформа ECO AIOps.
- Офлайн-утилита `eco-pack.exe` (или вкладка «Мастер пакета» в платформе).
- Не нужны Rust, Node, Python и доступ в интернет. Prod-ключ подписи автору
  не выдаётся: пакет подписывает ИБ после проверки.

## 2. Формат исходников

Манифест писать вручную не обязательно: если у автора есть только `AGENTS.md`
и навык, платформа сгенерирует `manifest.json` сама (см. 2.1). Ручное
редактирование нужно только для нестандартных возможностей (свои `bin`-tools,
MCP-подключения, `external_writes`).

Исходники — обычная папка (или её zip). Минимальная структура:

```text
my-app/
├─ manifest.json              # схема 2; JSON Schema: docs/manifest.schema.json
├─ AGENTS.md                  # допустимая замена prompt/system.md в корне
├─ SKILL.md                   # допустимый корневой навык
├─ prompt/
│  └─ system.md               # системный промпт
├─ skills/                    # необязательно
│  ├─ main/
│  │  └─ SKILL.md
│  └─ index/
│     └─ SKILL.md
└─ bin/                       # необязательно: exe-инструменты пакета
   └─ tool.exe
icon.svg                     # необязательно: иконка карточки
```

Необязательные поля карточки:

- `"description": "одна строка до 160 символов"` — показывается под названием;
- `"icon": "icon.svg"` — только SVG, ≤128 КиБ, путь внутри пакета. Иконка
  рендерится как `<img>` и проходит строгую проверку: запрещены `<script>`,
  `<foreignObject>`, `<image>`, события `on*`, внешние `href`/`url(...)`,
  DOCTYPE. Невалидная иконка не ломает установку — карточка показывает
  буквенный аватар. Иконка входит в `hashes`.

Правила:

- `manifest.json` и `prompt/system.md` обязательны.
- Навык — папка `skills/<имя>/SKILL.md` (один уровень; вложенные папки
  хешируются, но движок читает `SKILL.md` только на первом уровне).
- Скилов может быть несколько: каждый — отдельная папка со своим `SKILL.md` и
  ресурсами. При одном скиле его текст встраивается в промпт; при нескольких
  платформа добавляет индекс и инструмент `platform_skill` (`list`/`read`), и
  модель загружает нужный скил по имени. Порядок и зависимости опишите в
  `AGENTS.md` → `prompt/system.md`.
- Пути в манифесте — только относительные, без `..`, абсолютных путей и `:`.
- В исходниках не должно быть секретов, ключей, токенов, `.env`, логов и
  собранных артефактов платформы (`.data`, `engine/`, `sessions/`).
- Если пакет содержит `bin/*.exe`, к исходникам прикладываются: исходный код
  инструмента, команда сборки, версия и SBOM/список зависимостей.

### 2.1. Если есть только AGENTS.md и навык

Мастер пакета умеет собирать манифест из уже существующих исходников:

| В исходниках | Что делает мастер | В манифесте |
|---|---|---|
| `AGENTS.md` в корне | переносит в `prompt/system.md` | `profile.system_prompt` |
| `prompt/system.md` | оставляет как есть | `profile.system_prompt` |
| `SKILL.md` в корне | переносит в `skills/main/SKILL.md` | `hashes` |
| `skills/<имя>/SKILL.md` | оставляет как есть | `hashes` |
| `bin/*.exe` | оставляет, показывает в логе | `tools` нужно объявить вручную |

Порядок: «Мастер пакета» → папка → «Загрузить» → проверить `app_id` и название →
выбрать шаблон (`files` — если нужен доступ к рабочей папке) → **«Создать манифест
из исходников»**.

Мастер создаёт `manifest.json` со схемой 2, версией `0.1.0`, подключением `llm`,
`file_scopes: ["workspace"]` для шаблона `files`, `artifacts` и пустыми `hashes`.
Файлы `AGENTS.md` и `SKILL.md` при импорте переносятся (не копируются) в
`prompt/system.md` и `skills/main/SKILL.md`, чтобы не дублироваться в zip. Если
такие файлы нужны вам отдельно, сохраните копию до импорта. Если ошиблись с шаблоном, выберите нужный и нажмите **«Применить шаблон к
манифесту»** — мастер поправит `capabilities.file_scopes` без пересоздания
пакета. После изменения манифеста нужны новые `build` и `sign`. Версию, `publisher`
и `min_shell_version` правьте в манифесте после генерации.

## 3. Манифест

Обязательные поля:

| Поле | Значение |
|---|---|
| `schema_version` | `2` |
| `app_id` | латиница, цифры, `-`, `_`; уникален |
| `name` | отображаемое имя |
| `version` | semver `x.y.z` (понижение запрещено) |
| `profile.system_prompt` | путь к промпту, обычно `prompt/system.md` |

Необязательные, но важные:

| Поле | Значение |
|---|---|
| `min_shell_version` | минимальная версия платформы, `x.y.z` |
| `publisher` | кто выпускает пакет (заполняет ИБ/владелец) |
| `profile.model_hint` | подсказка модели (`gateway-default`) |
| `profile.max_steps` | лимит шагов агента (например, `20`) |
| `capabilities.file_scopes` | `["workspace"]` — доступ к файлам рабочей папки |
| `capabilities.external_writes` | id MCP-подключений с правом записи |
| `connections` | `llm` обязателен; `http-mcp` — только если нужны MCP-инструменты |
| `tools` | инструменты пакета: `tool`, `bin`, `argv`, `stream` |
| `artifacts` | квоты дампов (`quota_mb`, `ttl_hours`) |
| `hashes` | заполняется автоматически (`eco-pack build`) |

Доступы:

- Без `file_scopes: ["workspace"]` агент не получит `list_files`, `read_file`,
  `write_file`, `append_file`.
- `artifact_list`, `artifact_search`, `artifact_read` доступны всегда: это
  read-only доступ к дампам сессий приложения (`dumps.ndjson` и сохранённому
  полному выводу крупных tool-результатов). Так агент сам дочитывает усечённый
  вывод, без ручного поиска в панели артефактов.
- Платформа сама добавляет в системный промпт раздел «Инструменты платформы»
  со списком доступных инструментов и правилами (файлы, скилы, артефакты,
  пакетные exe, MCP). Не дублируйте этот список в `prompt/system.md` — он
  генерируется из манифеста и всегда совпадает с тем, что реально доступно.
- Все пути файловых инструментов относительны рабочей папке; выход за неё
  блокируется платформой.
- Remote MCP write-инструменты не выдаются без `capabilities.external_writes`.
- `tools[].stream`: `read` или `write`; write-инструменты стоит использовать
  только для действительно изменяющих операций.
- Сетевой доступ есть только у LLM-gateway и объявленных MCP-подключений.
  Пакетный exe — отдельный код: на прототипе он не в песочнице, поэтому
  доверяйте только проверенным бинарям.

### 3.1. MCP-подключения

Пакет объявляет только **id подключения**, без URL и токенов:

```json
"connections": [
  { "id": "llm", "type": "llm", "required": true },
  { "id": "context7", "type": "http-mcp", "required": false }
],
"capabilities": {
  "external_writes": []
}
```

- **Где настраивать сервер**: глобально — платформа → «Настройки» → «Реестр
  MCP-серверов»; для конкретного пакета — вкладка «Настройки приложения» в его
  рабочем пространстве. Один и тот же `id` может иметь разные endpoint, токен и
  TLS-политику в разных приложениях: app-override имеет приоритет над глобальной
  записью. Определение и токен хранятся в DPAPI и в пакет не попадают.
- **Права записи**: remote MCP write-инструменты не выдаются, пока id не добавлен
  в `capabilities.external_writes`. Read-инструменты доступны без этого.
- **TLS в закрытом контуре**: если сервер использует private CA или self-signed
  сертификат, в настройках MCP есть отдельный переключатель «Не проверять
  TLS-сертификат». Он отключает проверку цепочки и имени хоста только для этого
  подключения; включайте его осознанно и фиксируйте в заявке ИБ.
- **Имена инструментов у агента**: `<connection>_<tool>` (например,
  `context7_resolve-library-id`).
- **Инструменты сервера объявляются в `tools[]`**: по одной записи на каждый
  инструмент, только `tool` и `stream`, без `bin`/`io`/`argv`/`secrets`:

  ```json
  "tools": [
    { "tool": "resolve-library-id", "stream": "read" },
    { "tool": "get-library-docs", "stream": "read" }
  ]
  ```

  `connections` без таких записей не даёт модели ни одного remote-инструмента:
  автоподхвата из `tools/list` нет. Имя `tool` должно совпадать с именем
  инструмента сервера; если оно совпадает с id подключения, проверьте
  `tools/list` — обычно это признак, что взяли id вместо имени инструмента.
- В рабочей среде вкладка «MCP-инструменты» появляется, если у пакета есть
  `http-mcp`; там доступен ручной вызов и аудит.

Мастер пакета:

- при импорте ищет `.mcp.json`, `mcp.json`, `.vscode/mcp.json`,
  `opencode.json(c)` и добавляет найденные id как `http-mcp` (без URL/токенов,
  запись выключена); инструменты сервера при этом **не** добавляются — их
  объявляют в `tools[]` вручную по именам из `tools/list`;
- в разделе «MCP-подключения» показывает объявленные id, статус «сервер настроен /
  нет в настройках» и переключатель «запись»;
- добавить вручную: id + «разрешить запись» → «Добавить MCP»
  (`pack_set_mcp`). После изменения манифеста — новый `build` и `sign`.

Перед установкой убедитесь, что сервер с тем же id зарегистрирован в настройках,
иначе remote-инструменты не появятся (аудит покажет отказ).

### 3.2. Скрипты, сервисы и `.env`

Скрипты внутри `skills/` **не исполняются автоматически**: они попадают в пакет и
`hashes`, но модель получает только текст `SKILL.md`. Чтобы код действительно
запускался, его нужно оформить как инструмент пакета — `tools[].bin` (exe; при
необходимости собранный PyInstaller/аналогом). Инструментов может быть несколько;
у каждого своя JSON-схема аргументов, `stream` и `secrets`.

Пакетный exe запускается с очищенным окружением: он не видит `ECO_LLM_KEY`,
`ECO_AGENT_TOKEN` и пользовательские переменные. `TEMP/TMP/SystemRoot` платформа
передаёт сама.

`.env` в пакете запрещён: `eco-pack validate/build` завершится ошибкой
`secret material must not be packaged`. Файлы `.env*`, `*.pem`, `*.key`,
`*.p12`, `*.pfx`, `id_rsa*`, `credentials*` в пакет не попадают.

Правильный способ подключить скрипт к сервису — сопоставление переменных
окружения с секретами DPAPI в манифесте:

```json
"tools": [
  {
    "tool": "sync",
    "bin": "bin/sync.exe",
    "io": "json",
    "parameters": {
      "type": "object",
      "properties": {
        "action": { "type": "string" },
        "query": { "type": "string" }
      },
      "required": ["action"]
    },
    "secrets": {
      "SERVICE_URL": "svc_url",
      "SERVICE_LOGIN": "svc_login",
      "SERVICE_PASSWORD": "svc_password"
    }
  }
]
```

- `io: "json"` — аргументы модели приходят в stdin одним JSON-объектом, а stdout
  возвращается как результат (JSON парсится, иначе текст). Файловый режим
  (`io` не указан или `files`) остаётся для конвертеров с `input`/`output`.
- `parameters` — JSON Schema аргументов; без неё модель получает свободный объект.
- Для `io: json` не используйте `{input}`/`{output}` в `argv` — платформа это
  отклонит.
- В Python скрипте замените `dotenv`/`.env` на `os.environ["SERVICE_LOGIN"]` и
  `os.environ["SERVICE_PASSWORD"]`; соберите exe (PyInstaller) и положите в `bin/`.
- Один и тот же секрет можно указать в нескольких инструментах — пользователь
  вводит значение один раз.

1. Значения `svc_url`, `svc_login`, `svc_password` пользователь сохраняет либо
   в «Настройки → Хранилище секретов (DPAPI)» как общие, либо в «Настройки
   приложения → Переменные инструментов» — тогда они действуют только для этого
   пакета. App-значение имеет приоритет; если его нет, используется общее.
2. При вызове инструмента прокси подставляет их в env **только этого процесса**,
   на время вызова. В пакет, манифест и логи значения не попадают.
3. Если секрет не задан, вызов отклоняется с понятной ошибкой (fail-closed).
4. Имена env-переменных — `A-Z`, `0-9`, `_`; имена секретов — латиница, цифры,
   `-`, `_`, `.`.
5. Секреты per-user: на каждой машине пользователь вводит свои значения.

Если сервис умеет MCP, предпочтительнее не скрипт, а `http-mcp`-подключение:
endpoint/токен хранятся в DPAPI, аудит и права записи такие же, но не нужно
собирать и подписывать exe.

Не рекомендуется класть `.env` в рабочую папку: файловые инструменты агента
могут его прочитать, а содержимое уйдёт в LLM. Секреты — только через DPAPI.

## 4. Промпт и навыки

- Промпт описывает роль, границы, формат ответа и чего делать нельзя.
- Навык — пошаговая инструкция: «когда применять», «шаги», «ограничения».
  Пишите конкретные пути и имена файлов, которые агент должен использовать.
- Не дублируйте пароли, URL с токенами и внутренние адреса.
- Держите файлы небольшими: промпт/навык — единицы-десятки КиБ.
- Примеры: `examples/file-notes/prompt/system.md`,
  `examples/file-notes/skills/main/SKILL.md`.

## 5. Сборка, подпись, установка

В платформе: вкладка **«Мастер пакета»**.

1. Скопируйте исходники в рабочую папку автора (пример из репозитория не
   собирайте на месте).
2. Укажите папку, загрузите файлы.
3. Если `manifest.json` ещё нет — проверьте `app_id`/название и нажмите
   «Создать манифест из исходников».
4. `Проверить` — до первой сборки ожидаемо ругается на `hashes`.
5. `Собрать zip` — пересчитывает `hashes` и создаёт `<app_id>-<version>.zip`.
6. `Подписать` dev-ключом (только для локального теста).
7. `Установить` — пакет появляется в каталоге (нужен trust anchor профиля).

CLI:

```powershell
eco-pack validate D:\apps\my-app
eco-pack build D:\apps\my-app
eco-pack sign D:\apps\my-app --key D:\keys\me\dev.key
```

`build` меняет `manifest.json` (блок `hashes`), `sign` создаёт
`manifest.sig`. Не коммитьте их в исходники и не передавайте dev-ключ
вместе с пакетом.

## 6. Что передавать на проверку и в ИБ

Передавайте:

1. Zip исходников **без** `manifest.sig`, `hashes`-сборки и dev-ключей
   (или git-репозиторий с тегом версии).
2. Собранный `eco-pack build` zip — для сверки `hashes`.
3. Для `bin/*.exe`: исходники, команду сборки, версию, SBOM/зависимости.
4. Changelog и `min_shell_version`.

ИБ проверяет код и содержимое, подписывает prod-ключом, добавляет версию в
allowlist. После этого пакет можно тиражировать.

## 7. Чек-лист перед передачей

- [ ] `eco-pack validate` без ошибок после `build`.
- [ ] В промпте и навыках нет секретов, абсолютных путей и `..`.
- [ ] `file_scopes`/`external_writes` минимальны.
- [ ] Пакет ставится в чистый профиль и открывается.
- [ ] Агент создаёт/читает файл только в рабочей папке.
- [ ] Попытка `read_file("../secret.txt")` отклоняется.
- [ ] `bin`-инструмент (если есть) не требует сети и не читает чужие папки.
- [ ] Аудит `audit/<app_id>.jsonl` содержит вызовы инструментов.
- [ ] Версия не ниже установленной; `min_shell_version` корректен.

## 8. Частые ошибки

| Симптом | Причина |
|---|---|
| `hashes` не покрывают файлы | не выполнен `eco-pack build` |
| `manifest.sig` отсутствует/невалиден | пакет не подписан или манифест изменён после подписи |
| `downgrade rejected` | версия ниже установленной |
| `min_shell_version` | пакет требует более новую платформу |
| `path must stay inside the workspace` | абсолютный путь, `..` или symlink за пределы папки |
| Инструмент не появился у агента | не объявлен `tools[]`/`file_scopes`/`external_writes` |
