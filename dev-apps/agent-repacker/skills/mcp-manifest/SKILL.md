# MCP в манифесте

MCP объявляется **на двух уровнях, и нужны оба**. Это не альтернативы и не
взаимозаменяемые варианты.

1. **Сервер** — одна запись в `connections`, только id и тип:
   `{"id": "doc_mcp", "type": "http-mcp", "required": false}`.
2. **Каждый инструмент сервера** — отдельная запись в `tools[]`, только `tool` и
   `stream`, **без** `bin`, `io`, `argv`, `secrets`:
   `{"tool": "query", "stream": "read"}`.
`tool` — точное имя инструмента из `tools/list` сервера, а не подпись из UI и не
придуманное имя. Оно может совпадать с id сервера — это допустимо, если сервер
действительно так называет свой инструмент (проверь `tools/list`), но чаще
означает, что в `tools[]` попал id сервера вместо имени инструмента.

Платформа выставляет инструмент модели как `platform_<connection_id>_<tool>`,
например `platform_doc_mcp_query`.

## Канонический пример

```json
"tools": [
  { "tool": "validate_dsl", "bin": "bin/difytools.exe", "io": "files" },
  { "tool": "plugin_catalog", "bin": "bin/difytools.exe", "io": "json" },
  { "tool": "query", "stream": "read" },
  { "tool": "system", "stream": "read" }
],
"connections": [
  { "id": "llm", "type": "llm", "required": true },
  { "id": "doc_mcp", "type": "http-mcp", "required": false }
],
"capabilities": {
  "file_scopes": ["workspace"],
  "external_writes": []
}
```

Итог у модели: `platform_validate_dsl`, `platform_plugin_catalog`,
`platform_doc_mcp_query`, `platform_doc_mcp_system`.

Если серверов несколько, каждая запись без `bin` дублируется под каждым
`http-mcp`-id. Поэтому для двух серверов с разными наборами инструментов не
оставляй «общий» список без `bin`: раздели инструменты по смыслу или оставь
один сервер, иначе у модели появятся лишние комбинации.

## Запись без bin — это норма

`{"tool": "eco_support_query", "stream": "read"}` в `tools[]` — **не ошибка** и
не «инструмент без исполняемого файла». Отсутствие `bin` — единственный признак
remote MCP-инструмента. Не проси добавить к такой записи `bin`, `io` или
`secrets` и не называй её сломанной.

## Антипаттерны (именно они ломают пакет)

| Ошибка | Почему плохо | Правильно |
|---|---|---|
| `{"tool": "<id сервера>", ...}` без сверки с `tools/list` | обычно это id сервера, а не инструмент; при совпадении получится `<id>_<id>` | точное имя инструмента; запись допустима, только если сервер реально отдаёт инструмент с таким именем |
| только `connections`, без записей в `tools[]` | сервер не даёт инструментов: они **не** подтягиваются автоматически из `tools/list` | по записи `{tool, stream}` на каждый нужный инструмент |
| `{"tool": "MCP Reply"}` / подпись из UI | это не имя инструмента; регистр и пробелы не совпадут с сервером | точное имя из `tools/list` |
| `"bin"`/`"io"`/`"secrets"` у remote-инструмента | игнорируются и создают ложное впечатление файлового инструмента | только `tool` и `stream` |
| сервер в `tools[]` вместо `connections` | сервер не запускается, инструмент не появится | сервер — в `connections` |

## Перед сохранением

- [ ] Все `http-mcp`-серверы перечислены в `connections` (id + тип, без URL).
- [ ] Для каждого нужного инструмента каждого сервера есть запись
      `{tool, stream}` в `tools[]`.
- [ ] Имена сверены с `tools/list`. Если имя совпадает с id сервера, убедись, что
      сервер действительно отдаёт инструмент с таким именем, а не что ты взял id
      подключения.
- [ ] Имена взяты из `tools/list`. Если `tools/list` неизвестен — перенеси имена
      из промпта/скилов источника и отметь в `REPORT.md`, что их нужно сверить с
      сервером.
- [ ] `stream: "write"` только для меняющих инструментов, а id сервера добавлен
      в `capabilities.external_writes`.
