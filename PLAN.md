# План сборки desktop-платформы мини-приложений для ИИ-агентов

Дата: 2026-11-13. Статус: черновик для обсуждения.

## 0. Что строим

Самодостаточное Windows-приложение-платформа: пользователь устанавливает один инсталлятор и
дальше загружает в него **упакованные подписанные мини-приложения**. Мини-приложение — это
агентская возможность: свой профиль агента, свой набор инструментов, свои скилы, свои
требования к подключениям. Первое приложение — разбор алертов и логов, второе может быть
работа с документами Word, третье — что угодно ещё.

Платформа даёт общее: установку и реестр приложений, UI, движок агента, keychain, аудит,
политику артефактов, контроль прав. Мини-приложение даёт только данные и поведение —
и никогда не расширяет права.

Внутри одного мини-приложения пользователь видит чат с агентом, экран требуемых подключений,
структурированный результат и экспорт отчёта.

## 1. Архитектура

```
┌───────────────────────────────────────────────────────────────────┐
│ Платформа: Tauri shell (Rust) + WebView2                          │
│  ├─ Реестр приложений: установка, версии, включение, удаление     │
│  ├─ UI: лаунчер, чат, настройки подключений, результат, экспорт   │
│  ├─ Сессии: один инстанс движка на приложение, запуск по запросу  │
│  ├─ tool host: прокси, allow-list, потоки, лимиты, гейт записи    │
│  ├─ keychain (DPAPI), короткоживущие токены, аудит-буфер          │
│  └─ политика артефактов и квот                                    │
└───────────────────────────────────────────────────────────────────┘
     │ stdio MCP                        │ HTTP
     ▼                                  ▼
 eco-logs.exe / doc-app.exe       LLM-gateway (внутренний)
 (инструменты приложения)               │
     │                                  ▼
     └──────────► OpenSearch / Sentry / MCP-Hub (через gateway)
```

Два инварианта:

1. **UI и движок не общаются с инструментами напрямую.** Все вызовы идут через tool host,
   где живут allow-list, разделение потоков, лимиты, гейт подтверждения и маркировка.
2. **Приложения изолированы друг от друга.** Каждое видит только свои инструменты, свои
   подключения, свои артефакты и свой профиль. Вызовов между приложениями нет — маршрутизацию
   выполняет оболочка, что заодно закрывает требование об оркестраторе.

## 2. Зоны и границы доверия

| Зона | Расположение | Права | Содержимое |
|---|---|---|---|
| trusted packages | `C:\Program Files\<Продукт>\apps` | запись админ, проверка подписи при каждой загрузке | подписанные мини-приложения |
| user config | `%LOCALAPPDATA%\<Продукт>\config.json` | пользователь | включённые приложения, endpoint, модель, TTL, квоты |
| secrets | DPAPI + короткоживущий токен на приложение | только процесс оболочки | ключи, токены подключений |
| app state | `%LOCALAPPDATA%\<Продукт>\apps\<app_id>\` | только эта сессия приложения | артефакты, кэш, локальный аудит-буфер |
| reports | каталог по выбору пользователя | пользователь | готовые отчёты, durable |

Иммутабельность обеспечивается **подписью при каждой загрузке**, а не ACL: пользователь
владеет своей папкой, но изменённый пакет не загрузится.

## 3. Контракты

### 3.1 Пакет мини-приложения

```
package.zip
  manifest.json
  manifest.sig            # Ed25519, detached
  bin/*.exe               # Authenticode-подписан
  src/                    # исходники для ревью и SBOM
  prompt/system.md        # системный промпт агента (хешируется)
  skills/*.md             # playbooks
  sbom.json
```

`manifest.json`:

```json
{
  "schema_version": 2,
  "app_id": "eco-logs",
  "name": "Разбор алертов и логов",
  "version": "1.4.0",
  "min_shell_version": "1.0.0",
  "publisher": "CN=...",
  "profile": {
    "system_prompt": "prompt/system.md",
    "model_hint": "coding",
    "max_steps": 25
  },
  "tools": [
    {"tool": "search", "argv": ["--tool", "search"], "stream": "read"},
    {"tool": "dump",   "argv": ["--tool", "dump"],   "stream": "write"}
  ],
  "connections": [
    {"id": "llm",        "type": "llm",        "required": true},
    {"id": "opensearch", "type": "opensearch", "required": true},
    {"id": "sentry",     "type": "sentry",     "required": false}
  ],
  "capabilities": {
    "index_allowlist": ["bo-*", "eco-*"],
    "file_scopes": ["session"],
    "external_writes": []
  },
  "docs": [
    {"id": "report", "label": "Отчёт по инциденту", "export": ["md", "docx"]},
    {"id": "defect", "label": "Дефект", "export": ["md"]}
  ],
  "artifacts": {"quota_mb": 500, "ttl_hours": 168},
  "hashes": {"bin/eco-logs.exe": "sha256:...", "prompt/system.md": "sha256:..."}
}
```

Правила: `argv` фиксирован манифестом, модель не формирует команды; неизвестный `tool`
отклоняется до запуска процесса; несовпадение хеша или подписи — отказ загрузки
(fail-closed) с понятной ошибкой и записью в аудит; `capabilities` не расширяются
пользователем, только разработчиком при выпуске новой версии.

Требуемая версия оболочки проверяется при установке и при каждом запуске. Понижение версии
приложения блокируется.

### 3.2 Поверхность UI мини-приложения

Три уровня, из них в v1 — первые два:

1. **Общая поверхность (обязательна).** Чат, настройки подключений, сгенерированные из
   `connections`, просмотр результата, экспорт. Приложение управляет только данными.
2. **Декларативные панели (опционально).** `ui.panels` с фиксированным словарём виджетов:
   форма, таблица, markdown, список файлов, кнопка запуска, привязанная к tool. Произвольного
   JS нет.
3. **Webview-субапп (вне v1).** HTML/JS от вендора в изолированном контейнере с типизированным
   мостом. Отдельное решение и отдельная оценка рисков.

Смысл: «мини-приложение» должно ощущаться отдельным продуктом (имя, иконка, свои поля и
свой вид результата), не открывая при этом новую поверхность исполнения кода в рендерере.

### 3.3 Конверт ответа инструмента

```json
{
  "summary": "12 340 совпадений, 4 приложения, пик 14:05–14:20",
  "aggregates": [{"app": "bo-web", "count": 8123}],
  "samples": ["...до 20 строк..."],
  "truncated": true,
  "spill_path": "sessions/<guid>/dump-3.ndjson",
  "bytes": 65536,
  "took_ms": 812,
  "redactions": 47
}
```

Лимит на `bytes` — в бинаре, по умолчанию 64 КиБ. Превышение не обрезается молча: либо
агрегация, либо выгрузка в artifact. `dump` при превышении квоты падает с ошибкой.

### 3.4 Работа с артефактами

- `dump` и экспорты пишут только в каталог сессии; путь подставляет хост, не модель.
- `artifact(query)`: текстовый поиск (regex, счётчики, первые N строк) и field-query по
  NDJSON (`filter`, `group_by`, `count`, `limit`). In-process, без `rg.exe`.
- Ответ `artifact` проходит тот же конверт и тот же лимит, что и остальные tools.

### 3.5 Политика временных файлов

| Параметр | Значение по умолчанию |
|---|---|
| каталог | `%LOCALAPPDATA%\<Продукт>\apps\<app_id>\sessions\<guid>\` |
| session store движка | там же, `...\<guid>\engine\`; удаляется вместе с сессией |
| документы сессии | `...\<guid>\report.md`, `defect.md`; сохраняются только экспортом |
| квота на сессию | 500 МБ, 100 файлов |
| глобальная квота | 5 ГБ, 500 файлов |
| удаление при закрытии сессии | да |
| осиротевшие сессии (после крэша) | удаляются на старте, если старше 24 ч |
| фоновая уборка | раз в сутки, сессии старше 7 дней |
| низкий диск (<5 ГБ) | предложение очистки с топ-3 сессий |
| сохранение сырья | только через явный экспорт в reports |

В аудит попадают только метаданные (создание/удаление, байты, число строк, запрос).
Обещание «безопасного удаления» в документации не даётся.

### 3.6 Ядро агента

Движок — **opencode**, пиннится по версии, лежит в `Program Files` рядом с оболочкой,
обновляется вместе с ней, лицензия проверяется до включения в дистрибутив.

Почему он: из коробки закрывает те пункты требований, которые иначе писать самому —
permissions `allow/ask/deny` на уровне инструмента, локальные и удалённые MCP-серверы,
хуки через плагины, headless-сервер `opencode serve` с паролем и CORS, то есть встраивание
как sidecar по HTTP.

Правила интеграции:

| Правило | Реализация |
|---|---|
| Единственный MCP-клиент — оболочка | в конфиге движка один `type: local` сервер: прокси оболочки; он раздаёт tools одного приложения |
| Белый список вместо чёрного | `"permission": {"*": "deny"}` плюс точечные `allow` на MCP-инструменты; builtin `bash/edit/write/read/patch/webfetch/task` отключены |
| Пользовательский конфиг недоступен | `HOME`, `USERPROFILE`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME` указывают в каталог сессии; глобальные конфиги, скилы и плагины пользователя не подхватываются |
| Конфиг не редактируется | генерируется оболочкой на старте сессии в read-only temp, путь задаётся явно |
| Один провайдер | baseURL = LLM-gateway, список моделей ограничен, ключ из keychain |
| Плагины | автоустановка отключена, разрешён только встроенный набор |
| Состояние сессии | session store перенесён в каталог сессии и удаляется вместе с ней |

**Pi** — альтернатива, если нужен минимальный цикл, полностью контролируемый вами: меньше
кода для ревью, но permissions, MCP-клиент, хуки, session store и аудит пишутся с нуля и
дальше сопровождаются вами. Для прототипа годится; для промышленного продукта — плохой
трейд.

### 3.7 Файловая модель: у агента нет файловых примитивов

`bash/edit/write/read/patch/webfetch/task` отключены не потому, что «файлы запрещены», а
потому что у агента три разных вида вывода, и каждый реализован типизированным инструментом
со своим scope.

| Вывод | Кто пишет | Куда | Ограничение |
|---|---|---|---|
| Отчёт по инциденту | агент через `doc.*` | `report.md` в сессии | структура из скила пакета |
| Артефакты (дампы) | инструмент пакета, не модель | каталог сессии | путь даёт хост, квоты, TTL |
| Дефект на разработку | агент через `doc.*` | `defect.md` в сессии | структура из скила, наружу не уходит |

**Формат хранения — markdown, структура — из скила.** `report.md` и `defect.md` лежат
обычными файлами в каталоге сессии: открываются любым редактором, диффятся, вставляются в
Jira и Confluence. У агента нет пути к файлу, только id документа.

Структуру документа определяет скил пакета, а не платформа: какие разделы, в каком порядке,
какие якоря. Манифест объявляет только id, подпись в UI и форматы экспорта. Отдельных
шаблонов в манифесте нет — иначе появится второй источник правды, который разойдётся со
скилом.

Инструменты — формат-независимые примитивы над markdown:

- `doc.list()` → документы с ревизиями;
- `doc.read(id)` → markdown + ревизия (хеш файла);
- `doc.create(id, initial_md)`, `doc.append(id, md)`, `doc.insert_after(id, anchor, md)`,
  `doc.replace_block(id, anchor, md)`, `doc.finalize(id)`;
- якоря `<!-- id: x -->` расставляет инструмент при вставке; их имена приходят из скила;
- вызов с устаревшей ревизией отклоняется — ручные правки пользователя не теряются.

Секционной семантики (`set_section('timeline', ...)`) нет: платформа не знает, что такое
таймлайн.

Голый `write` не используется: перезапись целиком теряет ручные правки, создаёт гонки с UI,
жжёт токены и не даёт показать diff.

Дефект — такой же документ, ничем не отличается по механике: `defect.md`, свободный
markdown. Ничего никуда не отправляется: `doc.finalize` помечает документ готовым, UI
предлагает сохранить, и пользователь сам решает, куда его нести.

Приложение по построению read-only: `external_writes` пуст, пишущих инструментов в
allow-list нет, единственные записи — локальные файлы в каталоге сессии. Механизм
подтверждения внешних операций в платформе остаётся, но это приложение его не объявляет.

Экспорт в docx собирается из markdown произвольной структуры.

Движок при этом конфигурируется так:

```
"tools": { "bash": false, "edit": false, "write": false,
           "patch": false, "read": false, "webfetch": false, "task": false },
"permission": { "*": "deny", "eco-logs_*": "allow" }
```

Проверить на используемой версии: формат ключей для MCP-инструментов и то, что отключение
`read` не ломает загрузку скилов. Инструмент `skill` — тоже файловый примитив: его источники
ограничиваются каталогом скилов пакета.

## 4. Фазы

### Фаза 0. Спайки и решения (2–3 недели)

1. Подпись пакета: проверка до запуска кода, обход только с приватным ключом.
2. Изоляция процесса инструмента: чтение профиля пользователя вне грантов — включая
   junction, короткие имена, UNC, device paths.
3. EDR/AppLocker/WDAC: не блокируют ли запуск и не уводят ли exe в карантин.
4. Упаковка Python→exe (PyInstaller onedir и Nuitka): размер, старт, ложные срабатывания.
5. Сравнение форматов инструмента: декларативный / WASM / exe.
6. Движок: `opencode serve` + `permission: {"*": "deny"}` + прокси-MCP + подменённые
   `HOME`/`XDG_*` — доказать, что движок не подхватывает пользовательские конфиги и скилы,
   не вызывает builtin tools и не пишет сессии вне каталога сессии.

**Выход:** протокол спайков с числами, решение по формату инструмента, решение по
поверхности UI (уровни 1–2 или сразу 3).

### Фаза 1. Платформенное ядро (3 недели)

- Tauri v2, MSVC, per-machine install в `Program Files`, офлайн-бандл WebView2.
- Реестр приложений: установка из файла/сетевого пути, список, включение/отключение,
  удаление, отображение версии и подписанта.
- Keychain (DPAPI), bootstrap-аутентификация, получение токенов подключений.
- Генерация экрана настроек из `connections`, кнопки «Проверить подключение».
- Экспорт отчёта.

**Приёмка:** установка на чистую машину без Python и ручных шагов; установка и удаление
мини-приложения не требует перезапуска платформы; секретов нет ни в конфиге, ни в логах.

### Фаза 2. Первое мини-приложение: логи (3–4 недели)

- `eco-logs.exe` как долгоживущий stdio MCP-сервер: 11 команд + `artifact`; `sentry.exe`:
  6 команд. Один пакет, одна подпись.
- Конверт ответа, лимиты, allow-list имён tools, белый список индексов, лимиты размера и
  времени запроса.
- Изоляция файловых операций, квоты, очистка по §3.5.
- Скилы-плейбуки с маршрутом `analyze → verify → hist/impact → trace → dump+artifact`.

**Приёмка:** 30k-строчная выгрузка не попадает в контекст модели; выход за каталог сессии
отклоняется; индекс вне белого списка отклоняется; приложение не делает внешних записей.

### Фаза 3. Движок и замороженный профиль (3–4 недели)

- Движок (opencode) в `Program Files`, пиннится по версии, обновляется вместе с оболочкой.
- Один инстанс движка на приложение, запуск по требованию, остановка после простоя.
- Конфиг движка генерируется оболочкой в read-only временный путь; пользователь его не видит.
- Подменённые `HOME`/`USERPROFILE`/`XDG_CONFIG_HOME`/`XDG_DATA_HOME`, session store в каталоге
  сессии.
- Промпт берётся из подписанного пакета, хеш виден в UI, не редактируется.
- Tool host: allow-list по `tools`, потоки read/write, hard gate на внешнюю запись (в eco-logs
  не объявлен по `external_writes: []`), запрет bash/edit/web.
- Изоляция сессий разных приложений, перезагрузка контента только на границе сессии.

**Приёмка:** ни одно приложение не видит tools, подключения и артефакты другого; вызов
инструмента вне allow-list невозможен; запись требует подтверждения в UI.

### Фаза 4. Второе мини-приложение (2–3 недели)

Небольшое приложение на документы, одно из назначений — проверить общность контракта.
Требование по умолчанию: **оболочка не меняется**.

**Приёмка:** если для добавления второго приложения потребовалась правка платформенного
кода — контракт пакета признаётся неполным и пересматривается. Это архитектурный тест, а
не демо.

### Фаза 5. Идентичность и аудит (2–3 недели)

- Токен на приложение с коротким TTL, отзыв, маркировка `X-Agent-Id` (app_id + version),
  `X-User`, `X-Request-Id` во всех исходящих вызовах.
- Локальный буфер аудита с отправкой в централизованный Observability: запросы и ответы
  LLM, tools, MCP; метаданные по артефактам; без токенов (АС.5.13).
- Псевдонимизация пользовательских идентификаторов в ответах по умолчанию.

**Приёмка:** в логах конечных систем видно, какое приложение выполнило операцию; отзыв
токена прекращает его работу без переустановки платформы.

### Фаза 6. Пайплайн контента и релиза (3 недели)

- Релиз пакетов через АС DevOps; проверка `schema_version` и `min_shell_version`; защита от
  откатa; ротация ключей подписи; матрица совместимости платформа × приложение.
- Сборка и Authenticode-подпись инсталлятора и exe; SBOM; SAST/SCA для инструментов и скилов.
- Позитивный тест на утечки: сборка падает при обнаружении секретов и секретных сегментов
  URL MCP в артефакте.
- Проверка скилов, формирующих документы: для каждого хранится эталонный образец, на сборке
  проверяется, что из него получается валидный markdown с требуемыми полями отправки.
- Вендоринг crates/npm как резервный офлайн-путь сборки.

**Приёмка:** обновление приложения — новый подписанный релиз; откат на старую версию
блокируется; тест на утечки краснеет на подложенном секрете.

### Фаза 7. Пилот и подготовка к аттестации (4+ недели, зависит от внешних)

- Маппинг «требование → компонент → доказательство» — первый артефакт фазы, не последний.
- Threat model, согласование исключений EDR/AppLocker, отправка артефакта вендору AV.
- Пилот на 3–5 пользователях с фейковым OpenSearch/Sentry в тестовом контуре.

**Приёмка:** пилот без ручных обходов политик; пакет документов для ИБ собран.

## 5. Риски

| Риск | Влияние | Снижение |
|---|---|---|
| AV/EDR блокирует запуск exe | блокирует пилот | спайк в Фазе 0, Nuitka, подпись, ранняя отправка вендору |
| Контракт пакета окажется неполным | переделка ядра под каждое приложение | второе приложение как архитектурный тест (Фаза 4) |
| Приложения делят общий state | утечка данных между доменами | изоляция каталогов и токенов по `app_id`, тест на пересечение |
| Прямые вызовы OpenSearch под общей УЗ | нет атрибуции, нет отзыва | токен на приложение и маркировка (Фаза 5) |
| Агент забивает диск дампами | инцидент на АРМ | квоты в бинаре, падение `dump` вместо урезания |
| Модель игнорирует агрегации | стоимость, качество | жёсткий конверт ответов, маршрут в скилах |
| Требования трактуются иначе, чем мы | переделка перед аттестацией | маппинг требований в начале Фазы 7, ревью ИБ после Фаз 2 и 5 |

## 6. Открытые вопросы

1. Классификация: платформенный агент, ассистент на АС СК или общедоступный ассистент. От
   этого зависит применимость половины требований.
2. Поверхность UI: достаточно ли декларативных панелей или приложениям нужен webview-субапп.
3. Выдача отдельного `client_id` на каждое мини-приложение в централизованной системе ключей.
4. Bootstrap-аутентификация: SSO/device-code или сертификат установки в DPAPI/TPM.
5. Внутреннее зеркало crates.io/npm: есть или нет.
6. Право записи в trusted packages: только админ или self-service.
7. Схема доставки релизов приложений: АС DevOps, внутренний репозиторий, что-то ещё.
8. Политика хранения артефактов и ПДн: числа TTL, квоты, требования к псевдонимизации.
9. Движок: берём апстрим opencode с пином версии или поддерживаем собственный форк
   (как Kilo). От этого зависит процедура обновлений и срок сопровождения.

## 7. Non-goals

- Не давать агенту файловых примитивов: доступ к диску только через типизированные
  инструменты со scope (отчёт, артефакты, дефект).
- Не позволять мини-приложению вызывать инструменты или данные другого мини-приложения.
- Не вшивать секреты в дистрибутив, включая общий LLM-ключ.
- Не делать allow-list, гейты записи и политику очистки редактируемыми из пакета приложения.
- Не поддерживать hot-reload исполняемого кода и промпта посреди сессии.
- Не строить Rust-артефакты локально без зеркала или вендоринга.
